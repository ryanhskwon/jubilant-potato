vLLM 0.33 · RTX PRO 6000 × 1 · Rocky Linux

jubilant-potato 실행 가이드

6개 모델을 vLLM으로 서빙합니다. GPU가 1장이라 한 번에 한 모델만 띄우고, 모든 작업은 ./serve.sh로 합니다. 저장소: github.com/ryanhskwon/jubilant-potato

실행 순서

  1. 받기와 설정

    git clone https://github.com/ryanhskwon/jubilant-potato.git
cd jubilant-potato
cp .env.example .env   # 외부에 열면 VLLM_API_KEY 설정

  2. 점검

    드라이버(R580 이상), 이미지의 vLLM·transformers 버전, 모델 폴더를 확인합니다. 모델별로 이미지 안에서 실제 로드까지 해 봅니다.

    ./serve.sh check

  3. 모델 실행

    실행 중인 모델은 자동으로 내려갑니다. 첫 실행은 10분 이상 걸릴 수 있습니다.

    ./serve.sh up qwen3.8-27b-nvfp4

  4. 테스트

    test는 텍스트, 도구 호출, 이미지, 속도를 점검합니다. loadtest는 동시 사용자 수별 응답 속도와 초당 토큰을 잽니다. eval은 코딩 과제 통과율을 봅니다. 자세한 내용은 아래 모델 선택 평가를 참고하세요.

    ./serve.sh test
./serve.sh loadtest
./serve.sh eval

  5. 연결

    코딩 에이전트 같은 OpenAI 호환 클라이언트에서 http://<서버>:8000/v1로 연결합니다. API 키는 .env의 VLLM_API_KEY, 모델 이름은 아래 표의 API 모델 이름입니다.

지표 수집

부하 테스트: 동시 사용자를 1, 2, 4, 8, 16, 32로 늘려 가며 다음을 잽니다.

  • 첫 토큰까지 시간 (p50/p95)
  • 사용자당 출력 속도
  • 전체 초당 토큰

목표를 지키는 최대 동시 사용자 수도 알려 줍니다. 기본 목표는 첫 토큰 p95 5초 이하, 사용자당 15 tok/s 이상입니다.

./serve.sh loadtest --users 1,4,8,16 --input 8000 --output 512 --ttft 3 --tps 20 --csv result.csv

yaml의 max-num-seqs(기본 8)를 넘는 요청은 대기합니다. 한계를 재려면 32~64로 올리고 다시 측정하세요. 사용 비율이 20%라면 동시 사용자 8은 실제 사용자 약 40명입니다.

상시 수집: ./serve.sh monitor up 후 http://<서버>:3000에 접속합니다. 계정은 admin이고 비밀번호는 .env의 GRAFANA_ADMIN_PASSWORD입니다. 대시보드에서는 다음을 볼 수 있습니다.

  • 동시·대기 요청, 24시간 최대 동시 요청
  • 초당 토큰, 사용자당 속도
  • 첫 토큰 시간
  • KV 캐시 사용률, 캐시 적중률

모델 선택 평가

어떤 모델이 가장 적합한지는 품질과 속도를 따로 재서 정합니다. 품질은 eval, 속도는 loadtest로 잽니다.

1. 품질: 코딩 과제 통과율

모델이 실제 코딩 에이전트처럼 도구로 과제를 풉니다. 도구는 파일 목록, 읽기, 쓰기, 테스트 실행 네 가지이고, 테스트 통과 여부로 채점합니다.

./serve.sh up qwen3.8-27b-nvfp4
./serve.sh eval
# 과제 일부만
./serve.sh eval --only fix-median,cart-tax

출력 예:

과제                        결과   시간(s)   모델 호출   도구 호출   도구 실패
cart-tax                   PASS      95         6          9          0
fix-median                 PASS      40         4          5          0
...
통과 4/4 (100.0%), 과제당 평균 61.2초, 도구 호출 실패 0회

모델 비교 (results/eval/summary.csv)
| 모델 | 통과율 | 과제당 시간 | 도구 실패 | 토큰 | 날짜 |

실행할 때마다 results/eval/summary.csv에 모델별 한 줄이 쌓여서, 모델을 바꿔 가며 돌리면 마지막에 비교표가 나옵니다. 위 출력은 형식을 보여 주는 예시입니다.

2. 과제 만들기

샘플 4개(버그 수정, 함수 구현, 로그 파싱, 여러 파일 수정)가 들어 있습니다. 실제 업무에서 뽑은 과제 20~50개로 바꿔야 의미 있는 비교가 됩니다.

evals/tasks/<과제 이름>/
  task.md          지시문 (한국어 가능)
  files/           시작 코드 → 모델이 작업하는 폴더로 복사
  tests/test_*.py  채점용 unittest (실행 때마다 원본으로 덮어써서 모델이 못 고침)
  • 테스트는 시작 코드에서 실패하고, 올바르게 고치면 통과해야 합니다.
  • 과제 종류를 고르게 섞으세요: 버그 수정, 기능 추가, 리팩터링, 테스트 작성.
  • 모델이 작성한 코드는 서버의 임시 폴더에서 실행됩니다 (테스트당 60초 제한).

3. 속도와 수용량

같은 모델로 ./serve.sh loadtest를 돌려, 목표를 지키는 최대 동시 사용자와 초당 토큰을 잽니다. ./serve.sh test-all은 폴더가 있는 모든 모델에 대해 test, loadtest, eval을 차례로 실행하고 results/에 저장합니다.

4. 결정

  1. 품질 기준을 정합니다 (예: 통과율 70% 이상, 도구 호출 실패 거의 없음).
  2. 기준을 넘는 모델 중 최대 동시 사용자가 가장 많은 모델을 고릅니다.
  3. 필요한 기능을 확인합니다.
    • 이미지 입력: Qwen3.8, Qwen3.6, Gemma
    • 사고(thinking): Coder 두 모델 제외
    • 컨텍스트 길이
모델통과율도구 실패과제당 시간최대 동시 사용자사용자당 tok/s
eval의 비교표와 loadtest 결과를 이 형식으로 모으면 됩니다

트러블슈팅

공통 순서는 로그 확인 → configs/<모델>.yaml 수정 → ./serve.sh up <모델>으로 다시 실행입니다. yaml을 고친 뒤 다시 up 하면 바로 반영됩니다.

./serve.sh logs                                         # 전체 로그
docker compose --profile all logs | grep -iE "error|memory|KV cache"   # 핵심만
nvidia-smi                                              # GPU를 누가 쓰는지

메모리 부족 (OOM)

vLLM은 기동할 때 메모리를 미리 잡기 때문에, OOM은 대부분 기동 중에 납니다. 로그 문구로 어느 단계인지 보고 아래 순서대로 하나씩 적용하세요.

로그 문구원인조치 (위에서부터 시도)
KV cache is needed, which is larger than the available KV cache memory최대 컨텍스트 1개를 담을 KV 캐시 공간이 부족① max-model-len 절반으로 (131072 → 65536)
② gpu-memory-utilization: 0.95
③ kv-cache-dtype: fp8 확인 (Gemma 제외)
CUDA out of memory — 가중치 로드 중 (Loading weights 직후)모델이 GPU에 안 들어감① nvidia-smi로 다른 프로세스 확인 → ./serve.sh down, 남은 컨테이너 정리
② gpu-memory-utilization: 0.95
③ 더 작은 양자화(NVFP4) 모델 사용. Coder-Next(약 80GB)가 여기에 해당할 수 있음
CUDA out of memory — Capturing CUDA graphs 또는 compile 중CUDA graph·활성화 메모리 부족① speculative-config 줄 삭제 (MTP가 메모리를 더 씀)
② max-num-seqs 절반으로 (8 → 4)
③ enforce-eager: true 추가 (디코딩이 다소 느려짐)
No available memory for the cache blocks가중치를 올리고 나니 KV 캐시 공간이 없음① gpu-memory-utilization: 0.95
② 위의 CUDA graph 조치 적용
이미지 처리(encoder, profiling) 중 OOM이미지 입력용 메모리 예약① limit-mm-per-prompt의 image를 4 → 1
② 텍스트만 쓰면 language-model-only: true 추가
사용 중 OOM, 또는 긴 요청에서 컨테이너 종료긴 프롬프트 처리 중 활성화 메모리 급증① max-num-batched-tokens 절반으로 (8192 → 4096)
② gpu-memory-utilization를 0.90으로 낮춰 여유 확보

정상 기동 시 로그의 Available KV cache memory, GPU KV cache size: N tokens, Maximum concurrency for N tokens per request: Xx 줄을 보면 남은 여유를 알 수 있습니다. X가 1 미만이면 최대 길이 요청 1개도 못 담는 상태입니다.
